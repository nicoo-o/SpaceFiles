## 2. Règles de conduite (pour éviter les bugs inutiles)

1. **Une étape en cours à la fois, tous chantiers confondus.** On ne commence pas E4 tant que T2 n'est pas terminée ou explicitement
   suspendue par écrit. Les deux chantiers touchent les mêmes fichiers (voir § 5) : les mélanger produit des conflits invisibles.
2. **Une étape est terminée seulement si** : tout ce qu'elle annonce est fait ; `cargo build --release` lu ; `cargo test` lu avec un
   nombre qui **ne baisse pas** ; une capture si c'est visible ; un rapport avec les résultats exacts. Sinon elle est « en cours ».
3. **Le pur d'abord** : toute logique sans Win32 (carte, tri, catégories, liste blanche, grille de terminal, détection de shell,
   éditeur de ligne) s'écrit **avec ses tests avant** l'interface. Une interface branchée sur une logique non testée est la
   première source de bugs.
4. **Aucun code qui supprime avant son test de refus** : le test « un chemin hors liste blanche est refusé » existe et passe
   avant la première ligne qui appelle `IFileOperation` dans ESPACE.
5. **Jamais deux `cargo` en même temps** (le test `ecritures_concurrentes` échoue alors : vu le 17/11). Les nouveaux tests utilisent
   **chacun un dossier temporaire unique**, jamais `%TEMP%\spacefiles-test-archive` partagé.
6. **Pas de nouvelle dépendance ni de nouvelle fonction Windows sans mesure avant / après de l'exe**, écrite dans le rapport.
7. **Souris** : rien ne se teste à la souris ; chaque étape ajoute ses cas souris à `docs/ui/rodage-f1-2026-11-09.md`.
8. **Arrêt automatique** (on s'arrête et on le dit, on ne « contourne » pas) : le nombre de tests baisse ; l'exe dépasse le plafond
   décidé (§ 4) ; le résident dépasse 16 Mo ; un test n'est pas reproductible ; une étape révèle qu'une hypothèse du plan est fausse.
9. **Installer / commit / push** : seulement sur demande de l'auteur (« Installer », « Valide »). Jamais de push de `main`.
10. Entre deux étapes : l'état est écrit dans le plan (case cochée + chiffres) ; si la session grossit, `/clear` et reprise depuis
    ce fichier.

## 6. La boucle de chaque étape

1. **Cadrer** : relire la fiche de l'étape ; `graphify query` sur les fichiers touchés ; écrire en deux lignes ce qui sera vrai à la fin.
2. **Tests du pur** d'abord (rouge), puis le code (vert).
3. **Brancher** l'interface, le plus petit possible.
4. **`cargo check`, puis `cargo build --release`, puis `cargo test`** (jamais en parallèle) ; nombre de tests noté.
5. **`/snapshot`** si c'est visible (jamais au-delà de deux captures lues par moi ; au-delà, `regard`) ; cas souris notés.
6. **`rust-reviewer`** après tout `unsafe`, COM ou Win32 neuf.
7. **Rapport** : ce qui a changé, commandes avec résultats exacts, exe avant / après, ce qui n'est pas vérifié.
8. **Plan mis à jour** (case cochée, chiffres) puis **point d'arrêt** : l'auteur dit « Installer » ou « suivant ».

## 8. Ce que ce plan ne garantit pas

- Les tailles S/M/L et l'ordre des phases sont une **proposition** ; l'auteur peut les changer (par exemple faire le terminal avant ESPACE).
- Les listes de fichiers touchés sont des hypothèses tirées des plans, à confirmer dans le code.
- Les mesures de T0 et E0 viennent d'un seul PC, d'un seul build et d'une session élevée.
